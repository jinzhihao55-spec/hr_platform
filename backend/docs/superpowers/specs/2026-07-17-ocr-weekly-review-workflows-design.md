# OCR 与周报复核工作流设计

状态：已确认  
日期：2026-07-17  
目标分支：`feature/review-workflows-v1`

## 1. 背景与问题

单用户生产版已经能够：

- 将 OA/Release 和招聘图片识别为结构化事实；
- 为两类图片分别生成 `ocr_review_required` 决策；
- 在周五计算日报与周报，并对同一自然人的多条有效在职记录进行自然人去重。

当前界面仍有两个不可验收的缺口：

1. OCR 决策只显示“确认 / 替换输入”，不展示识别结果。用户无法进行有依据的确认。
2. 周报 `multiple_active_employments` 复核会把周报标记为“需要处理”，但没有生成可回答的复核项，也没有处理窗口。

## 2. 业务决策

同一自然人出现多条有效在职记录时采用以下正式口径：

- 事业部、项目和员工类型等周报归属维度一致：系统按自然人计 1 人，采用入职日期较新的记录作为周报归属；HR 必须确认后方可发布周报。
- 上述维度冲突：继续硬阻断，不允许在当前 Run 内人工覆盖计算；HR 必须创建同日修订 Run 并替换人员表。
- 日报和周报保持独立预览、独立校验、独立发布。周报复核不得阻断已通过的日报发布。

## 3. 范围

### 3.1 本次实现

- OA/Release OCR 结构化结果预览；
- 招聘 OCR 结构化结果预览；
- 非冲突重复在职记录的周报确认与解锁；
- 冲突重复在职记录的明细展示和同日修订 Run 入口；
- 周五有周报复核时默认打开周报，并显示明确处理入口；
- 确认、修订和发布行为进入现有 decision、validation、trace 与发布记录。

### 3.2 不在本次范围

- 保存或回显原始图片；
- 在当前已冻结 Run 中编辑 OCR 单元格；
- 在当前 Run 中手工指定冲突记录并覆盖确定性计算；
- 修改转签、外派等尚未冻结的业务口径；
- 多用户权限体系。

## 4. 安全与数据最小化

- 原始上传图片继续只存在于临时目录，解析后删除，不进入数据库、日志、备份或制品包。
- OCR 预览使用单独的受保护 API，不扩展通用 `RunDetail`，避免运行列表意外回显业务事实。
- Release 预览仅返回：来源行号、单号、申请日期、最后工作日、流程状态、Row5/Row30 分类和 OCR 状态。
- 招聘预览仅返回：来源行号、报表日期、是否合计行、上月 Offer 当月预计入职、当月 Offer 当月预计入职、识别标签和 OCR 状态。
- 周报重复在职预览仅返回该复核人员的姓名、工号、入职日期、事业部、项目、员工类型、状态和来源行号；禁止返回证件类型、证件号、`person_key` 或数据库主键。
- 所有响应受现有 Nginx 注入 token 和单用户网关保护；列表设置固定上限并保持确定性排序。

## 5. 后端设计

### 5.1 OCR 决策预览

新增：

`GET /runs/{run_id}/decisions/{decision_id}/preview`

接口校验 decision 属于当前 Run，且 `fact_ref` 为 `source:release:*` 或 `source:recruitment:*`。响应结构：

```json
{
  "kind": "ocr_source",
  "source_type": "release",
  "columns": [{"key": "order_no", "label": "单号"}],
  "rows": [{"source_row_no": 2, "order_no": "..."}],
  "warnings": ["原始图片按安全策略不留存；请核对结构化结果"]
}
```

接口只从 run-scoped `ReleaseFact` 或 `RecruitmentSnapshot` 读取白名单字段。

### 5.2 周报复核决策同步

周报计算已有 `review_items`。持久化周报校验时同步以下决策：

- `report_kind = weekly`
- `decision_code = multiple_active_employments`
- 稳定 `fact_ref = weekly:multiple_active_employments:{person_ref}`
- 非冲突项的唯一确认答案：`确认按自然人计1人`

同步规则：

- 相同 `fact_ref` 的已回答决策在重复预览时必须保留；
- 已消失的未回答周报决策删除；
- 冲突项不生成可解锁决策，继续作为 `BLOCK` 校验；
- `REVIEW` 校验只有在对应决策回答为 `确认按自然人计1人` 后才视为已复核；其他答案不得解锁周报。

### 5.3 周报复核明细

新增：

`GET /runs/{run_id}/weekly/review`

响应包含所有未通过的 `multiple_active_employments` 校验及其安全明细：

```json
{
  "items": [{
    "person_ref": "不可逆短引用",
    "severity": "REVIEW",
    "resolution": "confirm_dedupe",
    "decision_id": "...",
    "selected_source_row_no": 18,
    "employments": []
  }]
}
```

后端根据校验 evidence 中的短 `person_ref` 匹配当前 Run 的 `PersonIdentity.person_key` 哈希，再查询该人的 `EmploymentFact`。原始 `person_key` 不进入响应。

### 5.4 修订 Run

冲突项使用现有 `POST /runs`：

```json
{"report_date": "2026-07-17", "create_new": true}
```

新 Run 继承最近已发布日报基线，不复制已冻结事实或原始文件。用户需重新上传四类输入，确保输入证据与计算事实保持闭环。

## 6. 前端设计

### 6.1 当天运行页

- OCR 待确认卡片默认展开“识别结果”。
- 已确认卡片仍保留“查看识别结果”。
- 使用固定表头、横向滚动和稳定高度；不把表格嵌套在额外卡片中。
- 卡片明确显示“原始图片按安全策略不留存”。
- “替换输入”继续使用当前上传入口；输入冻结后改为“创建同日修订 Run”。

### 6.2 报表预览页

- 周报目标有 `review_count > 0` 或 `block_count > 0` 时，周报页顶部显示“周报复核”面板。
- 非冲突项展示全部相关在职记录，并标记系统采用的较新记录；按钮为“确认按自然人计 1 人”。
- 冲突项展示冲突字段，不提供确认按钮，只提供“创建同日修订 Run”。
- 确认成功后重新读取 Run 和周报预览；复核数归零时“发布周报”立即可用。
- 周五存在周报待复核时，进入预览页默认选择周报；日报仍可单独发布。
- 当天运行页的继续按钮文案改为“预览日报与周报”。

## 7. 错误处理

- 决策或 Run 不存在：404。
- decision 与 Run 不匹配、类型不支持：422。
- OCR 事实已被替换或不存在：409，并提示重新上传对应输入。
- 周报复核明细无法从 evidence 定位：保持发布阻断，返回可操作错误，不允许静默跳过。
- 决策重复提交保持幂等；回答与允许选项不一致时返回 409。

## 8. 测试与验收

### 8.1 后端

- OCR 两类预览字段白名单和确定性排序；
- 响应不包含证件字段、`person_key`、数据库 ID 或原图；
- 周报非冲突重复生成稳定决策，重复预览保留已回答状态；
- 确认后 `review_count` 归零并允许周报发布；
- 冲突重复保持 `BLOCK`，不能通过决策解锁；
- 同日修订 Run 不复制冻结事实；
- 日报发布不受周报专属复核影响。

### 8.2 前端

- OCR 待确认和已确认状态都能查看结构化结果；
- 周报“需要处理”时一定出现对应复核或修订动作；
- 确认后周报发布按钮解锁；
- 冲突项没有确认按钮；
- 桌面和移动视口无重叠，长字段可滚动且按钮文案完整。

### 8.3 实机验收

- 使用假 Release、假招聘截图完成前端上传、查看、确认、预览和发布链路；
- 使用假重复在职人员数据覆盖非冲突确认与冲突修订两条路径；
- 真实 7 月 17 日 Run 只做非破坏性页面复核，不修改已经确认的 OCR 决策答案。

## 9. 完成标准

- 用户不再看到没有处理入口的“需要处理”；
- 每个可确认动作都有可见证据；
- 每个不可确认阻断都有明确修复动作；
- 日报与周报均可从前端完成预览、复核、发布和追溯；
- 测试、隐私扫描和 Playwright 桌面/移动截图全部通过。
