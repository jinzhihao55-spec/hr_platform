## 1.2 输入输出与核心原则

**输入源（4 类，结构化 Excel 为权威源）**

| # | 输入源 | 必做 | 说明 |
|---|--------|------|------|
| ① | 人员表 | 是 | 结构化 Excel |
| ② | 离职人员报表 | 是 | 结构化 Excel |
| ③ | 协议签署 / OA | 是 | 结构化 Excel；截图为可选 OCR 旁证 |
| ④ | 招聘数据 | 是 | 结构化 Excel；截图为可选 OCR 旁证 |

**输出物（2 类）**

| # | 输出物 | 说明 |
|---|--------|------|
| ① | 员工数增减情况日报 | Sheet1 主表 40 行（按日追加日期列，照定稿）+ 在岗时长 |
| ② | 员工数增减周报 | Sheet2 主体维度 + Sheet1 成本中心维度 |

**核心原则**

- **MTD/YTD 链式累计**：日报基于「昨日已验收日报」顺推，不每天全量重算。
- **实际入离职**只认人员表事实；**提出离职 / Release** 与实际离职是两套口径，分别计入。
- **纳入口径**：只纳入正式员工、长期实习生、短期实习生、劳务人员；排除 P-合作伙伴、V-供应商、委托安置。过滤错误会导致全表偏差，必须阻断。
- **确定性要求**：数据清洗、字段映射、规则计算、导出流程必须模块化、可复现；LLM 只作交互入口或占位数据/校对，**不得硬编码到计算链**；关键输出需 trace package。
- **截图 vs 结构化**：冲突时一律以结构化 Excel 为准，差异记录到执行说明。

# 3. 流水线分层设计

## 3.1 Input Layer

职责：

- 文件上传接收
- Excel 解析（4 类输入源）
- 字段完整性校验（Pydantic，见第 5.1 节字段清单）

输出：

- 标准 DataFrame

## 3.2 Cleansing Layer

职责：

- P/V 员工过滤（纳入口径校验，硬阻断）
- 项目脱敏（`PROJECT_*`）
- MySQL 历史快照去重（流程单号、OA 单号、入离职事实）
- 转签人员识别留痕（当前暂不涉及自动排除，见 Q11）

输出：

- 干净但可能存在「非结构化备注」的数据

## 3.3 AI Node 1（结构化理解）

### 用途

- LWD（最后工作日）解析
- 非结构化备注转标准日期（`YYYY-MM-DD`）
- OA 等待审批、LWD 后补场景的状态标记

### 触发来源

| 来源 | 字段 | 典型场景 |
|------|------|---------|
| 离职报表 | 最后工作日 LWD ★ | 结构化日期，一般可直接使用 |
| OA 协议签署 | 最后工作日 LWD ★ | 可为空（等待审批），需后补 |
| OA 备注 / 人工补充 | 非结构化文本 | 「下月中旬」「月底」等模糊表达 |

### 示例

输入：

> 「Andrew补充LWD为下月中旬」

输出（解析成功）：

```json
{
  "lwd": "2026-07-15",
  "confidence": "high",
  "source": "oa_remark",
  "status": "resolved"
}
```

输出（LWD 缺失，Q5 已确认口径）：

```json
{
  "lwd": null,
  "status": "pending_lwd",
  "raw_text": "等待审批，LWD待补充",
  "affects_row5": true,
  "affects_row30": false
}
```

### 与 Pipeline 的衔接规则（Q5）

| 条件 | Row5（今日提出 Release） | Row30（本月 Release） |
|------|--------------------------|----------------------|
| 有 LWD，且 LWD 在本月 | 计入 | 计入 |
| 有 LWD，且 LWD 在下月 | 计入 | 不计入 |
| 无 LWD | 计入，打 `待补LWD` 标记 | 不计入；补充后再判本月/跨月并回补 |

长期缺 LWD 的单在执行说明中列出。

### 实现约束

- 参考基准日 = **报告日**（流水线运行当日）。
- 使用 `response_format = {"type": "json_object"}` 强约束输出。
- 解析结果写回 DataFrame，供 Pipeline Layer 消费；**不得**将 LLM 逻辑硬编码进公式计算链。

## 3.4 Pipeline Layer

职责：

- 纯规则计算，Pandas 多表关联
- 日报 Sheet1 Row2–40 逐行计算（见第 5.2 节）
- 在岗时长 Sheet 按事业部分组统计
- 周报 Sheet2 / Sheet1 双维度动态重算（见第 5.3 节）
- MTD/YTD 链式累计（基于昨日已验收日报）

输出：

- 待校验的日报/周报临时指标矩阵

## 3.5 Validation Layer

职责：

- 硬性公式链校验（★ 不通过不得交付）
- 跨表对齐（在岗时长 B10 = Sheet1 Row14）
- 输入源完整性、去重、LWD 判断、招聘取数交叉校验

详见第 5.4 节校验规则清单。校验不通过时拦截并交由 AI Node 6 处理。

## 3.6 AI Node 6（排障助手）

职责：

- 基于 MySQL 历史排障经验表（`ai_knowledge_base`）识别异常模式
- 给出自然语言解决建议
- 结合长记忆注入，辅助人工确认

## 3.7 Report Layer

职责：

- Openpyxl 精准注入原有 Excel 模板单元格
- 新列样式继承上一列；空白行（Row23/24/27/28/34/35）保持空白不填值
- 归档到 `project/日报/YYYY-MM-DD/`

# 4. 记忆机制设计规范 (Agentic Memory)

系统将 AI 节点从无状态调用升级为具备学习能力的轻量级 Agent。通过以下三层记忆架构实现系统的持续迭代。

## 4.1 短记忆 (Short-term Memory)

- **定义**：单次批处理任务（Task ID）内的上下文缓存。
- **职责**：保证同一批次 Excel 内部 AI 提取逻辑的一致性，避免重复推理，提升处理效率。
- **实现方案**：
  - 存储于 **Redis Hash** 中（如 `task:{task_id}:entities`）。
  - 存储内容：当前批次识别出的「人名映射」、「特定临时代称」等。
  - 生命周期：随流水线任务生命周期结束自动失效（TTL 过期释放）。

## 4.2 长记忆 (Long-term Memory)

- **定义**：跨批次、跨周期的企业历史业务经验沉淀。
- **职责**：作为外部知识库，解决特定业务黑话、隐性特征提取以及历史反复出现的逻辑排障。
- **实现方案**：
  - 存储于 **MySQL** 专属表（`ai_knowledge_base`）。
  - 存储内容：
    - 提取规则（如：「老东家=上一家履历公司」）。
    - 异常排障模式（`error_pattern`、`human_correction_method`）。
  - 注入机制：在 AI 节点请求前，基于当前数据的特征向量或关键字检索相关经验，作为 System Prompt 注入。

## 4.3 记忆回流 (Memory Consolidation/Reflux)

- **定义**：将人工经验（Human-in-the-Loop）自动转化为机器长记忆的自进化闭环。
- **触发机制**：
  1. **捕获 Diff**：前端用户在数据确认或排障页面，手动修改了 AI 的原始提取结果。
  2. **提炼知识**：后端异步触发 AI 任务，比对「原始输入 + AI 错误输出 + 人工正确修改」，调用 DeepSeek 进行经验总结。
  3. **规则入库**：生成结构化规则存入 MySQL 的长记忆表。
  4. **风控设计**：新入库的规则设定初始权重或置信度阈值，防止单次误操作污染全局长记忆库。

# 6. 技术选型理由

## 6.1 前端（React 18）

本系统前端承担「多源表格上传 → 流水线进度展示 → 校验结果审阅 → 人工修正 → 报表下载」的完整交互闭环，React 18 生态能较好覆盖这类**数据密集型内部工具**的需求：

1. **复杂表格与表单场景匹配**：日报/周报涉及大量行列数据、校验明细、Diff 对比（如 AI 提取 LWD vs 人工修正值）。Ant Design 5 的 Table、Form、Upload、Modal 等组件成熟稳定，适合快速搭建企业级数据确认界面，减少自研表格交互成本。

2. **人工确认闭环的天然契合**：架构图中前端与后端是双向交互——上传材料、展示校验失败项、接收排障建议、提交人工修正并触发记忆回流。React 的组件化与单向数据流便于把「任务状态 / 异常列表 / 修正表单」拆成可维护模块，状态变更可预测、易测试。

3. **TypeScript 保障字段契约一致**：输入源 4 类、日报 Row2–40、校验规则等与后端 Pydantic Schema 需严格对齐。TypeScript 可在编译期约束 API 响应结构与前端表单字段，降低「前后端字段名/类型不一致」导致的联调成本。

4. **轻量状态管理**：流水线任务进度、当前批次审阅上下文、修正 Diff 等状态用 Zustand 即可满足，无需引入 Redux 等较重方案，符合内部工具「功能够用、结构简单」的定位。

5. **生态与可维护性**：React 18 社区活跃、文档与人才储备充足；Concurrent 特性有利于大表格渲染时的交互响应。团队后续扩展（如增加「执行说明」编辑页、历史任务归档查询）可在同一 SPA 内渐进演进。

## 6.2 后端（Python 3.10+）

本系统后端本质是 **Excel ETL + 规则引擎 + AI 增强** 的数据流水线，Python 在该类场景中具有明显工程优势：

1. **Pandas 与业务计算模型一致**：日报 Row2–40 的计数、链式 MTD/YTD 累计、多表关联（人员表 × 离职报表 × OA × 招聘）、周报分组聚合等，天然适合 DataFrame 表达。用 Python 可避免在强类型语言中重复实现一套「表格代数」，开发与调试效率更高。

2. **Excel 读写链路完整**：`openpyxl` 支持按单元格注入模板并继承样式（校验规则 #11：新列样式继承、空白行保持空白），与 Report Layer「精准注入、不重建表格」的要求直接对应；`pandas.read_excel` 负责 Input Layer 多源解析，工具链成熟。

3. **FastAPI + Pydantic 对齐 Input Layer**：4 类输入源的字段校验（类型、必需性、枚举）可用 Pydantic Model 声明式定义，与文档第 5.1 节字段清单一一映射；FastAPI 自动生成 OpenAPI 文档，便于前后端联调与 Schema 同步。

4. **AI 与异步任务集成顺畅**：DeepSeek API 兼容 OpenAI SDK，Python 异步调用（`httpx` / `asyncio`）可嵌入 FastAPI；记忆回流「异步分析 Diff → 提炼规则入库」适合用后台任务处理，不阻塞主流水线响应。

5. **规则可测试、可复现**：核心业务计算要求「LLM 不得硬编码进计算链」。Python 便于将 Pipeline / Validation 各层拆成纯函数模块，配合 `pytest` 对 Row6=Row4+Row5、B10=Row14 等硬性校验编写单元测试，保证发布前校验规则可自动化回归。

6. **数据团队友好、迭代成本低**：人事报表口径会随业务确认持续调整（如 0623 清单中 Q1–Q16）。Python 脚本化特性使规则变更、口径补丁、临时对账脚本均可快速落地，无需频繁编译部署，适合需求仍在收敛阶段的内部系统。

## 6.3 AI 模型（DeepSeek）

本系统选用 DeepSeek API（`deepseek-chat`）作为 AI 能力组件，主要用于非结构化数据解析与异常诊断增强，其在本系统中的定位为「流水线中的轻量级智能中间件」，不参与核心业务计算，仅提供结构化信息抽取与自然语言解释能力。

1. **成本与性价比**：适合高频、批处理式调用，有利于控制长期运行成本。
2. **中文业务语义理解**：针对 OA 备注、人工补充说明、模糊时间表达等中文非结构化描述表现稳定。
3. **结构化输出能力稳定**：支持 `response_format = {"type": "json_object"}` 强约束输出，适用于字段补全与信息抽取。
4. **高吞吐与低延迟**：适合嵌入 FastAPI + Pandas ETL 流水线，避免明显性能瓶颈。
5. **工具化定位与架构适配性**：「规则引擎主导 + AI 能力增强」，保证流程确定性与可复现性。
6. **SDK 兼容性与迁移成本**：兼容 OpenAI SDK 调用规范，便于未来模型替换。
